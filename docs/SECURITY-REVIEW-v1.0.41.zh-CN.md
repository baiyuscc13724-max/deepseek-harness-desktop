# Harness Desktop v1.0.41 安全、权限与隐私审查

范围：代理团队项目任务/自动化/业务同步与桌面 Git 能力、Host-only 模型准入插件、女仆鲸结构化智能陪伴、壁纸视频生命周期与 Range 流式回归、会话生成停止后的自动跟随等运行时小修，以及统一发布器的全云端打包与既有不可变发布链。

## 当前结论

v1.0.41 继续保留官方 Harness 对主对话、模型配置和 Provider 凭据的所有权。本轮新增的项目任务、自动化与业务同步都在代理团队工作台内以显式命令门禁、角色权限和文件边界运行，不新增任意脚本执行、密钥读取或绕过用户确认的写接口；模型准入插件是有界的 Host-only 准入与排队门禁，饱和时拒绝而不是无限堆积；女仆鲸智能陪伴只使用桌面自身持有的结构化任务状态和本地记录，不读取对话正文、屏幕或文件。正式发布仍必须由统一可恢复发布器完成本地源码/安全门禁、GitHub Actions 全平台打包、Android、组件签名、CNB 镜像和 stable feed 门禁；发布器在本机删除并拒绝 `dist`，不会生成或采用本地正式包。真实结果完成前，本审查不把候选版本描述为已发布。

## 代理团队项目能力与权限边界

- 项目任务命令只接受规范化集合内的字段（如 `title`、`requirements`、`fileScope`），带命令 ID、期望修订号和最多 64 KiB 的命令体上限；创建、领取、依赖、转移与完成都经过业务域校验，拒绝重放与未知字段。
- 项目自动化默认不执行：定义需要创建/更新，运行需要人工 `approve`，`reject`、`retry`、`cancel` 走同一命令门禁；自动化输入做 canonical JSON 哈希绑定，不对任意脚本开放执行入口。
- 业务同步只接受 authority/collaborator 两种模式，成员角色固定为 `owner`/`maintainer`/`contributor`/`reviewer`/`observer`，任务与自动化权限按角色收敛；队列、并发和页项目数有限（如最大 1000 队列、100 对等端），消息必须规范化、有界并带摘要校验。
- 桌面 Git 能力只通过环境变量显式声明的授权根目录解析路径，`realpath`/containment 复核后落入 Git 根内才允许操作；不向模型开放任意工作区外 Git 命令。
- 以上项目能力全部复用既有团队 root/team/task/member/run ID 责任链与文件边界约束，本版不引入隐藏第三层嵌套代理。

## 模型准入插件

- `dsh-model-admission` 是 Host-only 插件（无 `dsh.client` 注入），随包分发并保持 unpacked 供 profile 安装；清单与桌面版本严格一致。
- 默认准入策略为 8 个活跃槽、32 个全局等待、每个根至多 8 个等待、30 秒超时，全部参数有硬上限；队列满、超时、取消或关闭均显式拒绝/释放，不无限堆积、不静默丢弃退出路径。
- 插件注入 `agents`/`llm`/`sessions` 只做有界等待与准入，不读取 Provider 凭据、不修改模型路由、不改变官方调度拥有的主对话行为。

## 女仆鲸智能陪伴的隐私边界

- 陪伴引擎只消费桌面已有的结构化任务状态（任务开始、多任务、等待决定、受阻、完成、长时间运行）和本地记录（默契/每日进度/连续完成）。
- 不读取对话正文、不读取屏幕、不读取文件；所有记录保存在本地，风格与主动陪伴开关可关闭，无云上传路径。
- 关系等级、风格枚举与 TOK 记录都是受边界校验的本地状态更新，不引入新的网络或文件系统权限。

## 壁纸与视频生命周期

- 视频壁纸继续通过受管文件的 `Range` 流式响应播放，禁止整段视频读入内存或序列化为 data URL；图片与视频预览都使用受管副本，单项、总字节、数量与原子替换门禁不变。
- 新增生命周期与视频流式回归测试覆盖受管导入、范围响应和清理；Wallpaper Engine 项目导入仍只扫描已知库路径并拒绝 scene/web/application 类型，不上传壁纸或对话内容。

## 会话与运行时补丁

- 生成停止后的自动跟随状态机只改官方会话视图的滚动跟踪行为，不触碰权限、存储或网络面；助手复制等运行时补丁以显式锚点替换并保留防重放/防回归断言，未引入新的 IPC 或特权接口。
- 内嵌浏览器继续绑定当前可见标签、精确 origin、稳定 request ID 与有效控制代次；密码、Cookie、Authorization、Token、银行卡、验证码和账户值仍禁止模型读写，敏感动作继续需要一次性用户确认。

## 发布与验证

- 桌面、全部随包插件、Android `versionCode 10041`/`versionName 1.0.41`、iOS build/marketing version、移动路由和发布工作流默认目标同步到 1.0.41。
- `release-manifest.json` 与三个 stable feed 在候选源码中继续指向上一健康版本；旧本地打包状态不能替代新源码门禁，断点 runId 必须重新绑定精确 workflow 路径/事件/提交/ref，并且每次真正进入 stable 阶段前都重新检查 GitHub/CNB 精确 18 项资产，全部通过后才原子提升 stable feed。
- GitHub→CNB 大文件保持云到云，禁止本机上传发布二进制；Android 继续使用 Actions Secret 中的长期 release 证书；macOS 继续执行显式无签名、双架构 DMG/ZIP、`安装.command` 与结构自检契约。
- 本地只在同一干净提交运行 `npm run verify`、`npm run verify:release`；发布器先删除 `dist`，调用编排器到 `verify` 后断言 `dist` 仍不存在，再创建不可变 `v1.0.41` Tag。
- GitHub `build`、`ios-simulators`、`stage-draft` 分别复核 Tag、checkout HEAD 与发布器 `productRevision` 一致；Windows 云端构建在上传资产前运行打包后自检与真实组件健康/回滚测试。
- 生产组件工作流只允许从不可变 Tag 的 `workflow_dispatch` 启动，拒绝可变 `component-publish/*` 分支；恢复工作流在云端再次核对 Tag 后发布器修复提交的六文件白名单。任何 Tag 移动、run 身份、Draft 快照、摘要、签名或双云字节不一致都失败关闭。
