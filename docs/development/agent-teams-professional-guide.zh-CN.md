# Agent Teams 专业能力与交付指南

适用范围：维护源码中的专业契约 v1。它说明产品的事实边界，不代表当前运行的旧安装已经更新，也不是发布验收凭证。

## 1. 只提出目标，不必设计团队

例如：

> 请改善任务页可读性，保留权限与 Stop 安全边界，补回归测试，并告诉我实际验证了什么。

负责人先判断是否需要团队。简单或紧密耦合的工作由一个模型完成；只有一条辅助工作流时使用普通辅助代理；两个以上持续且独立的交付方向才值得组成可见团队。职责名如“界面”“测试”只是人员标识，不能证明加载过技能或通过专业资格认证。

团队任务先明确实际产出、验收标准、依赖和不冲突的文件范围，然后再认领执行。成员提交不等于最终完成；负责人独立复核后才可解除下游依赖。

## 2. 如何理解专业技能状态

| 界面状态 | 实际含义 | 不代表什么 |
| --- | --- | --- |
| 通用任务 | 没有要求专门技能，仍能执行和交付 | 任务无效或必须额外安装 |
| 已绑定 | 当前任务解析到了指定技能 | 模型已读取技能正文 |
| 已加载 | 当前有效 claim 内，真实 `skill` 工具成功加载，证据通过运行时核对 | 专业认证、结论正确或最终质量通过 |
| 缺失 | 指定 exact name 未找到或不能调用 | 可以用相似名字或职责名冒充 |
| 未知/历史 | 证据不足或旧记录 | 自动升级为已验证 |

- `required_skills` 最多 8 个 exact kebab-case 名称；同名按首次出现顺序去重。
- 同名 provider 的选择遵循既有技能注册表优先级，不做语义合并。
- 运行时核对执行者、claim、lease、项目工作区及 Stop 代次。失败、取消、错误工作区、伪造内容、旧 claim 的结果不能变为当前加载证据。
- 证据记录 provider、来源、时间和正文哈希，不复制整份技能正文或内部资源路径到团队投影。
- 新 claim 必须有新的实际加载；不能承诺“加载一次永久有效”或“完全零重复上下文”。

## 3. 什么才算可复核交付

### 纯文本交付完全有效

任务可以只给出结论或说明。即使任务声明了可写 `files`，也不强制生成文件；只有 `requires_file_artifact: true` 才要求文件证据。

v1 的交付示意：

```json
{
  "summary": "检查完成",
  "content": "OK",
  "criteria": [
    { "criterion": "给出检查结论", "evidence": "实际交付正文为 OK。" }
  ],
  "limitations": ["结论范围仅限本次检查。"]
}
```

短而非空的正文有效，正文可以与摘要相同；不再以 32 字符作为最低门槛。摘要本身不能替代缺失的正文或文件。正文最多 16000 字符，空白正文不算交付。

### 文件交付

```json
{
  "summary": "报告已写入工作区",
  "artifacts": [{ "path": "docs/report.md" }],
  "criteria": [
    { "criterion": "提供检查报告", "evidence": "阅读 docs/report.md 的结论与限制章节。" }
  ]
}
```

`path` 是任务工作区内的相对文件路径。运行时计算实际文件大小和 SHA-256；不要自行提供哈希。绝对路径、`..` 越界、保留/私有目录、符号链接逃逸、不存在文件和超限文件会被拒绝。单文件上限 8 MiB，总文件上限 32 MiB。

提交后如果文件发生变化，负责人不能接受旧提交：需要重新整理交付并按最新任务状态操作。哈希绑定证明字节一致性，不证明内容的专业质量。

## 4. 提交、复核与完成是不同阶段

1. 成员使用当前 `claim_id` 和 `lease_epoch` 提交。运行时支持推荐动作 `submit`，并保留 `complete` 别名；两者都只进入 `submitted`。
2. `submitted` 表示等待负责人复核，仍不解除下游依赖，也不允许把成员或团队当作全部完成而退休。
3. 负责人读取真实交付，针对精确 `submission_id` 提供摘要、逐项标准/证据和限制，并使用最新任务 revision、pause epoch 与 request id 接受或拒绝。
4. 只有接受才进入 `completed`。复核质量标识为 `lead_reviewed`，不是 `host_verified`，也不是注册测试运行器的质量门禁证明。
5. 完全相同的合法重放按契约去重；不能把同一 claim 的另一份正文伪装成原提交重放。

旧记录保留为 `legacy_unverified` 等历史状态，不自动补写新版本的提交证据、执行者或负责人复核。重启恢复也不能把未知状态变成成功。

## 5. 新界面怎么用

默认先看：目标、当前工作、待复核数量、已完成成果，以及需要注意的问题。

- **与负责人继续对话**：打开该团队的确切负责人会话，再切到聊天；不会自动发消息、fork 或 resume。
- **工作详情**：按需展开三类工作列。等待复核仍属于进行中的工作，不会被显示为可再次认领。
- **已完成/取消历史**：保留在可展开历史中；取消不是成功。
- **任务详情**：查看正文、文件绑定、验收标准、复核及限制。协议元数据和诊断不再挤占每张概览卡。
- **技能**：区分绑定、真实加载、缺失和未知。缺少哈希/时间/真实工具来源时不会只凭 `loaded` 字样显示已加载。
- **授权提示**：信息完整且允许时显示正常状态；明确拒绝/撤销等显示需关注；授权缺失、部分字段缺失或未知时使用中性说明。未知不是“无需处理”，也不是自动要求重新授权。
- 草稿计划及团队 `attention` 会在一级摘要给出提示，不必展开诊断才知道。

界面使用原生按钮与展开控件。工作详情按钮展开并聚焦摘要；键盘 Enter 可打开任务详情。窄屏中的文字和按钮应折行，而不是横向溢出。

## 6. Stop、通信及真实性边界

- Stop 先关闭当前事件入口，再持久化暂停代次；旧加载、旧 claim、旧提交不能穿透这个边界。
- 重试、恢复、重新认领都必须遵循当前权威状态，不能绕过 Stop 或用户确认。
- claim 解析技能、submit 读取交付文件、accept 重读文件等异步等待前后，必须仍是相同的 live caller/root 对象及 canonical 工作区。等待中换目录或换成同 ID/同目录的另一 agent，也会拒绝，不悄悄借用新来源。
- 这是一致性围栏，不是冻结整个 registry、保证本机文件系统不可变，或解决不可观察的“离开后又回到原对象/目录”（ABA）。
- 已占满运行名额时，给已获准运行的成员发协调消息应复用其当前 steer 通道，而不是再申请一个模型名额。
- `queued` 只证明传输接受，不证明接收模型已读、更不证明任务完成。成员报告、checkpoint 或自然语言“完成了”不能替代持久化提交及负责人接受。

## 7. 验证方式与边界

相关回归：

- `tests/agent-teams-professional-capabilities.test.cjs`：真实公开工具、隔离持久存储、SkillRegistry 和技能 loader；模型生命周期用受控 fixture。
- `tests/agent-teams-product-experience.test.cjs`：完整客户端模块初始渲染适配器；不是 React DOM。
- `tests/fixtures/agent-teams-product-dom.cjs`：独立隐藏 Electron 窗口，实际 React/ReactDOM、Chromium DOM/CSS 与键盘输入；数据接口使用本地 fixture，不连接真实会话。
- 其余 Team 的 claim/OCC、Stop、生命周期、授权、依赖、通信、存储与 UI 测试必须一起保留。

源码检查、隔离浏览器检查、当前安装验证和正式发布验收是四种不同证据；任何一种都不能冒充另一种。正式版本必须按仓库发布器完成其独立门禁。
