# Harness Desktop v1.0.28 安全、权限与隐私审查

审查日期：2026-08-20。范围：代理团队独立会话视图、宿主持久化与投影、桌面更新幂等行为、移动版本同步、生产组件和不可变发布链。

## 当前结论

源码审查阶段未发现需要绕过既有安全边界的设计。正式发布仍必须通过干净提交、完整测试、发布契约审计、Windows 真实打包/自检/安装验证、GitHub 多平台矩阵、Android 长期证书、公开资产 SHA-256 复核和组件 Ed25519 验签；下文“待发布后填写”项目在获得真实证据前不视为完成。

## 官方能力优先

- 官方 DeepSeek Harness 固定为 `0.1.0-rc.8`，Electron 固定为 43.2.0。
- 代理团队使用官方 `conversation.view`，与“对话 / 轨迹”并列；不创建自定义路由、Portal 或第二套会话页。
- 对官方 view owner 的最小补丁只把既有 `actions.setView` 作为 `setView` 传给 `conversation.view` slot，使团队创建请求成功提交后能回到“对话”；不改变发送、会话所有权、路由或工具权限。补丁保持锚点校验和幂等，官方结构变化时失败而不是宽松注入；移除补丁后团队页仍可用，只退回中文提示让用户手动点“对话”。
- 成员实时工作复用官方可继续子代理会话和官方轨迹，不复制聊天、工具日志、编辑器、终端、模型选择或 Token 统计。
- 团队模型策略复用既有“主模型与子代理”路由：固定负责人始终是主模型；AI 按任务内容为成员选择主/子路由，普通任务默认子代理模型，高复杂推理、架构、安全关键或失败升级才使用主模型；未单独配置子代理模型时继承主模型。团队插件不新增 Provider、模型或密钥设置面。
- 删除旧 Agent Teams Modal、会话顶栏符号入口和输入 Dock，底部继续使用官方 composer。

## 代理团队权限边界

- 只有直接用户触发的最外层根会话可以创建团队；宿主常量 `HARD_MAX_TEAMS_PER_ROOT = 8`，同一 root 的第 9 个未关闭平级团队以 `AGENT_TEAMS_TEAM_LIMIT` 拒绝，不能通过设置提高。每个团队的负责人固定，嵌套团队和跨 root 连接均禁止。
- “启用自动团队”只写入设置，不合成用户消息、不填草稿、不调用模型或团队工具；策略从下一条真实的普通用户需求起判断。没有目标就没有请求，简单或不可并行任务由主模型负责人 solo 完成。自动模式不放宽 direct-human 根权限、团队/成员/并发硬上限或跨根隔离。
- 无活动团队、且只有一个独立的一次性辅助时，root 最多使用一个官方普通 `subagent`；只有至少两个需委派给不同成员的持续独立工作流，且确需依赖、交接、文件边界或汇总协调时才建立团队。普通 subagent 不冒充团队责任主体。
- 团队成员是可见、持久、可关停的责任主体，并被硬性禁止调用 `subagent`、`subagent_fork`、`workflow` 或 `ralph`。扩员只能由最外层 root 创建正式成员和持久任务，防止绕过 `maxMembers` / `maxActiveTurns`、文件冲突检查、原子认领及优雅/强制关停。
- 成员先持久化注册，再收到正式任务；协调中继使用 `coordinator` 来源，绝不伪装成用户消息。
- 任务保持依赖校验、原子认领、派生阻塞和文件冲突；同一负责人可建立跨团队依赖，宿主同时校验目标团队归属、任务存在性与全图无环。不同根会话之间的依赖一律拒绝。
- 跨团队中继只允许共同固定负责人发起，并要求明确来源/目标团队；普通成员不能借同名或会话 ID 穿越团队。跨根中继默认拒绝。
- `maxMembers` 对每个团队分别生效；`maxActiveTurns` 对同一 root 旗下所有未关闭团队合计生效，不能通过拆分团队获得额外并发，超限统一返回 `AGENT_TEAMS_ACTIVE_TURN_LIMIT`。两项设置值为 1–8，并受宿主硬上限约束。
- 关闭区分优雅与强制；孤儿恢复必须由另一个直接用户根回合显式预览和确认，不能转移负责人。
- Web UI 的“添加成员、创建任务、协调、汇总、请求关闭”只生成官方输入框草稿，用户检查并亲自发送后才可能调用模型工具。
- 创建草稿只有被官方输入状态观察到真实 `submitting → plain`、草稿修订已变化且内容被消费后才调用 `setView("chat")`；仅生成/编辑草稿、取消或失败不会切页，也没有 DOM 点击、自动发送或历史路由伪造。
- 用户只需提供目标；“自定义团队”和“添加成员”提示要求 AI 根据目标、任务缺口、成本、并行限制和文件冲突自行决定团队结构，不要求普通用户设计名称、职责、模型或文件分配，也不为了凑人数扩员。
- “添加协作团队”同样只生成草稿：AI 必须先按项目目标、现有团队分工和成本判断是否需要同级团队；现有团队足够时不创建，确需新增时才自动确定团队目标、成员、主/子模型、跨团队依赖和固定负责人中继。
- AI 只能在现有路由已提供的主/子模型策略内选择成员执行模型，不读取或复制 Provider 密钥。主模型升级仅用于明确的复杂度、安全关键或失败恢复，不得成为无条件扩张用量的理由。

## 名称、投影与消息隐私

- 自动规划提示要求成员使用“界面、测试、安全、文档”这类 2–6 字直白职责名，避免暴露“宿主、协调器、执行器、实现者、子代理”等技术称谓；宿主仍对所有新成员显示名执行 NFKC、空白折叠和大小写无关键比较，控制/格式/代理字符被拒绝，归一化重名原子拒绝。
- v1.0.27 已持久化名称继续按旧格式兼容读取；包含 ZWJ 表情或历史归一化碰撞的存储不会阻断插件启动。严格规则只用于新输入。
- UI 成员投影仅包含有界显示名、角色、可选模型、状态和活动时间；内部错误与宿主对象不外泄。
- 任务只投影标题摘要和依赖/阻塞/冲突元数据。非空文件范围无法证明不敏感时不返回路径，只返回稳定隐藏原因码。
- 团队消息正文和投递错误正文只保存在宿主侧；Web 工作区仅展示发送方、接收方、状态和时间。
- 普通协调中继在主聊天以官方折叠 notice 形式记录，摘要仅使用 locale-neutral 的 `Agent Teams`；模型上下文仍保留完整、可审计来源。

## 会话导航与实时可见性

- “查看实时工作”只对已被官方会话目录发现的健康 worker 地址显示；负责人自身和 `provisioning:*` 占位记录不提供无效入口。
- 打开成员使用官方 `sessions.subagentAddress()` 返回的精确地址，再调用 `sessions.openSubagent(address)`，不手工伪造父子地址。
- 团队工作区显示当前任务、状态和最后活动；同一负责人可查看并切换自己的多个团队及跨团队投递元数据，但不会获得其他根负责人的团队投影。完整流式输出及 Read/Edit/Test 工具时间线在官方成员会话与轨迹查看。
- 切换团队或切换到“对话 / 轨迹”只卸载 UI 并关闭 SSE/轮询，不调用中断、退役或关闭工具；所有相关团队成员继续在宿主侧后台运行。

## 更新、桌面与既有隐私边界

- 当前桌面已经是最新版本时，安装更新返回幂等成功并清除旧错误，不会把“无可用更新”误报为下载或安装失败。
- Renderer 保持 `contextIsolation: true`、`nodeIntegration: false`、`sandbox: true`；Browser、Computer Use、手机控制、记忆和缓存边界沿用 v1.0.27 已审查限制。
- 桌面清理继续永久排除会话、附件、记忆、工作区和活动 Runtime；本次版本更新不得清除用户授权状态。
