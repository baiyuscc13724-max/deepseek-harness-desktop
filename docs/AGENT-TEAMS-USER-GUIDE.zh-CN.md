# 代理团队（Agent Teams）用户指南

代理团队是一项**默认关闭的实验功能**。它让最外层负责人会话协调多个独立、可继续的成员会话；同一负责人还可以拥有多个平级团队，并在这些团队之间协调依赖与消息。它适合可以清楚拆分、需要并行推进的工作；如果只需要一次回答，普通会话通常更省事、也更节省模型用量。

## 先判断是否适用

**适用：**

- 一个目标能拆成研究、实现、测试、审阅、文档等相对独立的部分。
- 多个成员可以分别负责不同文件或不同只读调查，最后由负责人汇总。
- 工作持续时间较长，需要保留成员会话、任务状态和依赖关系。
- 你愿意为并行模型调用设置明确范围并关注预算。

**不适用：**

- 简单问答、一次性改动，或任务本身无法拆分。
- 多人必须同时编辑同一批文件，且没有明确的文件所有权。
- 你需要共享同一上下文窗口；团队成员拥有各自独立的上下文，并不会自动知道其他成员做过什么。
- 你希望仅凭创建旧团队任务就自动得到 worktree、自动合并或绝对无冲突保证；旧任务板仍只做协调。M5 Project Foundations 只会在负责人明确使用项目基础工具、真实 Git 根与资源声明通过 Host 校验后，才创建隔离 worktree并进入合并/质量门禁。
- 任务包含不应分发给多个模型会话的敏感内容。

## 开启与限制

1. 打开 Harness Desktop 的**设置**。
2. 进入**代理团队**设置区。
3. 开启“启用自动团队”。
4. 设置“每个团队的成员上限”和“同时工作的成员上限（所有团队合计）”，然后保存。不确定时保留默认值 4 和 4。

“启用”表示从你发送的**下一条普通需求**起，让 AI 自动判断是否需要团队。开关本身只保存设置，不会伪造用户消息、自动填入提示词或立即发起团队请求；没有目标就不产生请求，也没有团队开销。简单、不可拆分的任务由使用主模型的负责人 solo 完成，只有目标明确、复杂且确实可并行时才考虑组队。

启用后，“代理团队”页顶部的“自动团队已开启”区域会显示**关闭自动团队**。没有活动团队时，点击后会立即关闭并回到未启用说明；这个设置操作不发送消息、不写入提示词、不调用模型，因此不消耗模型 Token。若存在 `active`、`closing` 等任何未关闭团队，关闭按钮会禁用并提示先让负责人完成并关闭所有活动团队；关闭实验功能不会替你中断或关停团队。全部团队关闭后即可从同一页面关闭，也可以在设置中关闭。

两项设置都允许输入 1–8，默认都是 4。它们是**容量上限**，不是要求 AI 固定凑满的默认人数；AI 仍按真正独立且值得并行的工作流数量设计团队。完整快速建队和后续扩员都会读取当前设置，不再另行固定为 4 人。若希望一次最多启动 8 名可见成员，必须把两项都设为 8；只把“每个团队的成员上限”设为 8、而“同时工作的成员上限”仍为 4 时，第 5 个活动成员仍会被并发护栏拒绝。

“每个团队的成员上限”按团队分别计算；“同时工作的成员上限（所有团队合计）”由同一负责人旗下所有未关闭团队共同使用，不会按团队各自重新计算。数值越大并不一定越快：成员越多、同时工作的回合越多，模型调用量和费用通常也越高。实际可用并发还可能受模型服务商、账号额度和运行环境限制。

高级排障时，这两项在接口中分别名为 `maxMembers` 和 `maxActiveTurns`。后者超限返回 `AGENT_TEAMS_ACTIVE_TURN_LIMIT`。同一负责人最多保留 8 个未关闭团队，第 9 个返回 `AGENT_TEAMS_TEAM_LIMIT`；这个硬上限不能通过设置提高，自动模式下的安全限额也不会改变。

关闭实验功能前，应先关闭仍在活动的团队。关闭功能不会改变普通 `subagent`、`subagent_fork` 或 workflow 的行为。

## 必须从最外层负责人会话开始

创建团队必须满足两个条件：

1. 当前会话是最外层的根会话，而不是子代理、团队成员或嵌套会话；
2. 当前回合由你直接发送消息触发。

因此，请回到最外层的新会话或主会话，直接说“创建一个代理团队……”。不要在成员对话中要求新建团队。同一根负责人可以拥有多个平级团队；已获得本目标自动接力授权的负责人也可以在精确的后续 goal round 中建立确有必要的平级团队，但成员仍不能嵌套建团队。每个团队创建后固定由这个根会话负责；同项目 handoff/adopt 仍须直接用户明确操作。存在多个活动团队时，后续操作应明确团队名称或团队 ID。

如果系统提示必须由直接用户或根会话发起，回到最外层负责人会话，亲自重新发送请求即可。

## 推荐：像平常一样说需求

启用后无需先进入团队页，也不需要说“请创建团队”。回到“对话”，像平常一样发送下一条带有明确目标的需求即可。AI 会先判断：简单任务由负责人 solo 完成；只有复杂、可拆分且并行收益明确时才创建团队。普通用户不需要预先决定成员名称、人数、模型、职责或文件分配。

“代理团队”页里的模板只是希望立即指定协作方向时的可选入口。“自定义团队”会生成下面这种待审草稿：

```text
请根据以下目标判断是否值得组建团队：<可验证的最终结果>。
如果单人即可完成，请直接完成且不要组队；如果确实有至少两个可独立并行的工作流，
请先建立可追踪任务、先后关系和互不冲突的文件范围，再只添加必要成员。
负责人承担最终交付；不要为了凑人数创建成员。
```

“调研与核验 / 实现与审查 / 问题诊断”三个模板也只是协作方向，成员和任务仍由 AI 规划。工作目录、不能修改的内容、必须运行的检查或预算上限等硬约束可以和目标一起写明，但不要把手动设计团队当成使用前提。

开始后，可以继续用自然语言交给 AI 判断：

```text
根据当前目标和任务缺口判断是否需要增员；只有能明显减少重复工作且文件边界不冲突时才扩员，否则说明原因。
```

如果希望成员完成一个阶段后由负责人自动验收、调度下一步，而不是再次发送“继续”，请先在当前已创建且选中的团队负责人会话绑定一个 active Goal，再到“设置 → 代理团队”显式开启“自动接力，不用发送继续”。Desktop Host 会为这一次设置操作签发短时、单次消费的授权，并精确绑定当前 root、project、goal、team、pause epoch 和设置值；静态请求头、全局偏好或稍后才创建的首个团队都不能据此取得 Goal 权限。只有同一负责人下完整、仍存活且事实一致的团队组，后续平级团队才可继承这一精确授权。每个目标可配置自动追加 1–200 轮，默认额度为 200；这里限制的是 Agent Teams 的受控追加额度，不会改写当前会话 Goal 自己的 `maxGoalRounds` 配置。该功能开关默认关闭，升级旧版本也不会静默开启。Host/plugin 重启、Stop、handoff、关闭设置、降低额度、目标或安全事实变化都会先解除绑定 Goal 的激活，再轮换 Host 授权 epoch 并撤销本地授权；已有旧活动团队不会因升级或只打开开关而被静默接管。

```text
请列出所有团队、未完成任务、跨团队阻塞和文件冲突风险，不要为了提高并行数而新增成员。
```

## 先提交计划，再开始执行

新团队先形成可检查的计划 draft。draft 应列出目标、持久任务、依赖、负责人、文件或外部资源边界、所需能力，以及可能产生的外部副作用。只要计划仍是 draft，成员就不能启动，任务也不能认领或完成；“已经写进输入框”“负责人说可以”或出现成员占位都不等于计划已提交。

Host 提交计划时会绑定计划 hash 和 revision。完全相同的请求重放会返回同一计划，不会重复创建成员；如果任务、边界、权限、费用风险或外部副作用发生实质变化，必须重新检查并提交新 revision。公开添加成员必须同时绑定至少一个已经持久化的任务；无任务 spawn 会在启动成员前被拒绝。

任务工作区使用四个主区：

- **Ready**：计划已提交且前提满足，尚未持有有效 claim；
- **Running**：Host 已发布当前 attempt 和 claim fencing，成员正在执行；
- **Attention**：依赖、失败、权限 unknown、陈旧 claim、未确认外部副作用或其他事实需要处理；
- **Done**：Host 已接受当前 claim/attempt 的完成写入。

`Cancelled` 保留在历史中，不冒充 Done。页面不会根据模型措辞猜测“73% 完成”之类的百分比；只显示 Host 已验证的里程碑计数、attempt、最后活动时间和明确状态。成员提交的 checkpoint/下一步会标为**未验证自报**，可用于恢复上下文，但不是完成证明、权限证明或外部操作成功证明。

## 普通 subagent 与团队成员的区别

两者都使用独立上下文，但用途和生命周期不同：

- **普通 subagent**：无活动团队、且只有一个独立的一次性辅助时，root 可使用官方普通 `subagent`，例如单次检索或复核。它不是团队成员，不进入成员、任务和关停视图。
- **团队成员**：是工作区中可见、可继续、持久化的责任主体，有明确职责、正式任务、文件范围、状态和关停生命周期。

只有目标包含至少两个需委派给不同成员的持续独立工作流，且确实需要依赖、交接、文件边界或汇总协调时，才建立团队。一个辅助任务、串行工作或紧密耦合的改动继续 solo，必要时最多使用一个普通 subagent，不要为了形式创建团队。

团队成员硬性禁止调用 `subagent`、`subagent_fork`、`workflow` 或 `ralph`。需要扩员时，成员应通过 `team_expansion_request` 向固定负责人提交结构化建议，由最外层 root 评估后先建立持久任务、再创建可见的正式同级成员；成员不能私自派生不可见助手。这项禁令防止绕过 `maxMembers` / `maxActiveTurns`、文件冲突检查、任务认领和优雅/强制关停，确保这些控制覆盖全部实际工作。

运行时始终保持**负责人 → 可见同级成员**的扁平结构，不增加固定的“组长 → 干活组员”层。成员可以成为某个工作流的成果负责人，负责提出拆分、接收结果和复核验收，但这只是任务责任关系，不会获得创建成员或嵌套团队的权限。这样既能继续拆分复杂工作，又不会制造隐藏上下文、重复管理和难以核验的第三层调用。

结构化扩员申请必须引用申请者自己正在负责的 `in_progress` 任务，并为每个拟拆成果写清：独立交付物、可验证验收标准、互不重叠的文件或外部资源边界，以及并行后能缩短关键路径或提供独立复核的具体收益。宿主会拒绝非成员、非本人任务、待处理/已完成任务、超出当前成员/回合/任务容量、提案内部重叠的文件/资源边界，以及提案文件与**其他**进行中任务文件范围的冲突；申请本身只作为持久中继送给负责人，**不会自动建任务或创建成员**。

文件冲突采用保守范围判断：相同路径、目录与其子路径、以及 glob 的字面前缀都视为重叠，例如 `src` 与 `src/a.js`、`src/**` 与 `src/a.js` 会冲突，`src` 与 `src-a` 不会。Windows 按不区分大小写比较，Linux 等大小写敏感平台保留大小写。外部资源当前没有写入持久任务占用字段，宿主只能检查同一份申请内部的精确或以 `/` 分隔的层级重叠，**不能证明现有外部状态无人占用**；负责人必须在审批时核对数据库、服务、账号或远程环境等真实所有权。

负责人只在以下条件同时成立时批准：剩余成果确实可以并行；输入、交付物和验收足够独立；文件与外部状态所有权清楚；交接上下文较小；关键路径或独立复核收益明显高于协调成本；当前预算和容量允许。源母任务本身会从申请阶段的活动文件冲突比较中排除，否则 `files: ["src"]` 这类宽范围会让任何合理拆分都无法提出；但批准后，负责人必须先释放/重构母任务（必要时创建范围更窄的替代任务），确保它不再以宽范围保持 `in_progress`，再为每个接受的成果调用 `team_task_create`，最后用 `team_spawn` 创建可见同级成员。拒绝时应向申请者说明原因。高风险工作需要独立复核可以作为收益理由，但仍不能绕过边界和容量检查。

## 使用独立团队工作区

开启后，负责人会话顶部会出现 `对话 / 轨迹 / 代理团队` 视图标签。选择“代理团队”只会替换中央会话内容；左侧会话导航、顶部全局控件和底部官方输入框仍然保留。新会话仍默认打开“对话”。

当前工作区提供：

- **首次向导**：只需填写目标；可以选“自定义团队”让 AI 完全规划，也可选择“调研与核验 / 实现与审查 / 问题诊断”作为方向。AI 自行判断是否值得并行、需要多少成员、成员职责、任务依赖和文件边界。点击“放入输入框”后，完整请求会先写入官方输入状态，再立即切回“对话”供你检查；系统不会自动发送，你仍必须亲自确认。输入框只在“对话”视图出现，切换页面不会丢失尚未发送的草稿。
- **团队切换**：只有存在多个平级团队时才显示紧凑切换条；进行中的团队直接可见，已关闭团队收进默认折叠的“历史团队”。快捷提示“评估是否需要新团队”会让 AI 根据项目目标、现有团队分工和成本判断是否真的需要另一个团队；只有职责边界清楚且能独立并行时，才自动确定目标、必要成员和跨团队任务依赖。现有团队足够时，AI 应说明原因且不创建。切换团队或切到其他会话视图都不会停止后台成员。
- **当前工作**：主区域提供“团队画布 / 任务列表”两种仅查看视图，共用同一份团队状态。要创建、分配或完成任务，仍需在负责人对话中提出；系统会继续校验权限和任务状态是否为最新。画布从现有成员、任务、分配、依赖、阻塞和冲突信息生成，不会拖动任务或自动修改依赖；小屏或减少动态效果环境继续使用列表。任务变为 `completed` 后会自动移入默认折叠的“任务历史”。涉及非空文件范围时，页面会按安全策略隐藏具体路径，完整记录仍保留在本机服务中。
- **跨会话任务**：这是当前项目唯一的协作工作区，只显示当前 canonical 项目的顶层会话席位和项目任务，不按团队分组；同时提供依赖/移交、锁冲突/待决策、交付证据和变更历史摘要。独立 Project Tasks 底层仍保留为安全数据面，不再从 Agent Teams 暴露重复产品。
- **统一代理目录**：成员不会再在团队页复制一套常驻卡片或第二侧栏。点击页头“代理目录”或画布中的成员节点，会打开当前负责人已有的官方子代理目录；运行中的代理优先，其次为可继续代理，已结束记录保持默认收起并由用户手动查看。目录继续提供状态、Token、时长、嵌套关系和只读会话入口，“轨迹”仍使用官方视图显示 Read、Edit、测试等工具时间线。
- **协调记录与动态**：“协调记录”页和页头“动态”会显示谁向谁发送了协调信息、是否送达和时间，但不会展示消息正文；需要正文时请打开对应成员对话。按 `Esc` 或关闭按钮即可回到无侧栏的主工作区。同一负责人可以在自己的团队之间转交信息；不同负责人的团队默认隔离。
- **次要操作和设置**：“添加成员、评估是否需要新团队、创建任务、协调团队、汇总、请求关闭”默认收进“更多操作”；关闭自动团队等低频设置位于页面末尾的折叠“团队设置”。这些入口仍只生成草稿或保存明确设置，不会自动发送模型请求。生成草稿后页面会切回“对话”，你可以在唯一的官方输入框中检查并亲自发送。
- **关闭摘要**：团队关闭后默认打开它的任务历史；成员记录继续从统一代理目录查看，协作事件保留在按需动态侧栏，并提供创建下一团队的安全提示词入口。
- **连接状态**：“已更新”或“正在保持更新”表示页面仍在获取最新信息；看到“信息可能不是最新”时请刷新，看到“正在重新连接”时可稍候或返回对话继续工作。
- **跨会话任务**：原静态“团队工作流程”位置现在是当前 canonical 项目的协作工作区，展示顶层会话席位、项目任务表、依赖与两阶段移交、资源锁/冲突/待决策、交付证据与变更历史。它只观察、刷新、分页并写入负责人草稿，不按 Agent Team 分组，也不会自动执行任何操作。
- **定时与自动化**：左侧保留原会话的提醒；右侧是独立的项目自动化。项目所有者可以为一个真实项目任务建立单步规则，手动发起、明确批准，再由后台执行并保留运行记录。两者不会互相触发，也不会合并历史。
- **参与者与多人连接**：本机成员可以接收旧团队任务；其他电脑可以安全配对并建立端到端加密连接，还能同步“项目任务”和“项目自动化”的安全摘要。同步不会让远端人员变成旧团队任务的可分配成员，也不会公开设备标识、消息引用、摘要、路径、需求、评论、评审或原始账本。中转服务只能转发加密数据，不能读取内容，页面也绝不会展示设备私钥。

团队暂停时不会在后台继续；可点击“生成继续请求”，检查底部草稿后亲自发送。有成员失败时，固定负责人可以在失败成员恢复卡中明确选择“重试成员”或“替换成员”；两者都有确认、loading、success/error，绝不自动执行。其他操作失败也会同时给出下一步和技术详情，不会自动重试敏感变更。

创建成员、创建或分配旧团队任务、发送团队中继、普通退役成员和关闭团队等敏感变更，仍应在经过鉴权的负责人/成员会话中用自然语言提出，由模型工具执行。除失败成员 recovery 这个受信 Host 窄写入口外，工作区中的快捷操作只生成草稿，绝不代替你发送。切回“对话”或“轨迹”只会停止当前页面的实时监听，不会中断团队；成员会在宿主侧继续后台运行，再切回团队视图即可恢复最新状态。

## 跨会话任务：唯一的项目协作工作区

“跨会话任务”是 Agent Teams 唯一的项目协作入口，只订阅当前 canonical 项目。页面先展示真实顶层会话席位（职责、资源范围、阶段、下一步和更新时间），再展示项目所有任务表；任务属于项目而非团队，单个会话的 Agent Team 只作为执行摘要。页面还提供跨会话依赖与两阶段移交、冲突/资源锁/待用户决策、最近交付证据、变更历史及待协作请求的安全摘要；请求按 opaque requestRef 去重并显示响应期限，但不会自动唤醒或接管。

任务表使用后端全局 keyset 顺序，而不是只重排当前 DOM 页：**进行中 → 待评审 → 需处理（阻塞）→ 待开始 → 已完成 → 已取消**。每组先按显式业务 `priority`（高值优先），再按更新时间、创建时间和稳定 `taskRef` 破同分；页面显示精确总数与每组计数，完成区弱化但保持可访问，取消区独立置底。席位、任务、锁、移交、失败根恢复、证据、历史和协作请求各自有独立“加载更多”；点击后以服务端下一 keyset 页替换该区当前窗口，其他区不变。这样第 121 项以后仍能逐页完整到达，同时每次最多渲染 120 项，不无限增长 DOM/内存。每区游标为认证加密的 opaque keyset cursor；任务游标绑定状态秩、priority、更新时间、创建时间、taskRef、当前项目 lane 与 revision。篡改、跨项目重放、并发变更或应用重启后的旧游标都会安全失效，刷新/SSE 更新则从新 revision 的首屏重新建立顺序。24/120/128 KiB 只是页面与传输预算，不是项目总量。项目切换会清理旧列表，不扫描其他项目。独立 Project Tasks 与 Project Automation 底层基础设施继续保留，但不提供重复一级入口，也不存在 `project_task_*` 重复工具。

此工作区只观察、刷新和分页；每个真实顶层 root 是其 seat 唯一的项目板代表，并私下管理自己的 Agent Team。私有 Team 只服务当前已领取项目任务，成员只接收有界任务上下文并只使用 `team_task_*`，不能调用项目板工具。看板只显示有界 Team 摘要，不显示成员、聊天或完整团队任务上下文；Team 报告或完成不等于项目证据，root 必须核对交付并显式提交 evidence/status。协调 root 与参与 root 的权限彼此隔离。界面按钮不会伪装代理已执行，也不会添加成员级项目板控制。

新 root 在采用席位时及每个项目任务边界先读取请求，优先处理 `targetedToMe=true` 的项目。请求类型为依赖解除（`dependency_unblock`）、释放（`release`）、交接（`handoff`）、接管（`takeover`）；目标可 `accept`、`reject` 或 `release`。请求按期限 `respondByAt` 处理，只有工具返回 `escalationEligible=true` 才可审计解决；期限前必须由用户在当前 root 回合明确授权并由 Host 验证，不能靠模型自报。请求持久、去重且 no-wake：不要轮询，也不会自动唤醒已停止会话。

完成当前项并提交状态/证据后，以新的稳定 request id 调用一次 `claim_next`，继续领取一个可执行项目任务。每个 root 同时只保留一个制作中任务，手工 claim、所有进入制作中的 transition 和 `claim_next` 都在 transaction 内执行同一单活检查，不能批量囤积；多个 root 并发时同一任务只会被一个 transaction 领取。若任务被依赖或锁阻塞，先创建一个持久协作请求，再尝试其他工作。只有返回全部终态，或剩余阻塞都已有记录时才停止。

本节描述当前代码与固定接口契约，并不表示所有发布包或安装环境已经完成实机安装验证；实际可用性仍以所安装版本页面显示的能力状态为准。

## 项目自动化：手动发起、人工批准、后台执行

项目自动化和“当前会话提醒”显示在同一页，但它们是两套完全独立的能力：

- **会话提醒**只负责在原会话存活或恢复时提醒你，不会修改项目任务，也不代表工作成功。
- **项目自动化**跟随本机项目持久保存，操作的是真实 Project Task；它有自己的定义、运行、审批和核对记录，不读取或改写会话提醒历史。

当前首版刻意保持简单：一个自动化定义只包含一个项目任务状态变化，而且只能**手动发起**。使用顺序是：

1. 先在“项目任务”中创建真实任务，再打开“定时与自动化”。
2. 在“项目自动化”区选择任务和页面给出的目标状态，填写容易识别的名称并创建规则。首版不允许把自动化目标设为“待评审”或“已完成”，避免绕过提交、评审和验收。
3. 点击“手动运行”。系统会把规则内容和任务当前版本固定到这次运行；如果任务已被别人改变，会要求刷新，而不是偷偷套用新版本。
4. 在“等待批准”中再次核对并明确选择“批准”或“拒绝”。**批准只会放入执行队列，不等于已经成功。**
5. 后台 Runner 随后执行一次真实任务变更。页面通过运行状态和最近记录显示最终成功、失败或取消；不要只根据按钮点击或连接提示判断结果。

已启用的规则可以停用；等待批准、排队中或运行中的任务可以按页面当前允许的操作取消；只有服务端确认错误可重试时才显示“重试”。所有按钮还会在服务器端重新检查本机仍是项目所有者、规则/运行版本正确、目标任务和转换仍然有效。浏览器不能提交项目身份、执行身份、事件编号、审批编号、账本编号、路径或密钥。

项目自动化保留自己的幂等命令与 receipt 契约：连接中断时，当前自动化客户端最多使用**完全相同的请求内容**安全重试一次；版本冲突、服务器拒绝或意图改变时不会自动重试。这与上节 Project Tasks 浏览器“一次明确动作只发一个 POST”的契约不同。实时连接只发送“请重新读取”的失效通知，不携带可直接当作成功依据的运行内容。

项目自动化的 Runner 仍只在项目所有者所在电脑执行。协作者会看到安全同步的定义和运行摘要，但不会看到原始账本；只有主设备能力允许 `approve/reject`、当前运行仍处于等待批准且该运行的 `allowedActions` 同时允许时，才显示批准或拒绝。协作者不能创建、启停或手动发起规则。离线提交会保持同一请求等待主设备回执，页面不会乐观修改缓存；恢复连接后再以权威状态为准。它不会定时启动、不会自动批准、不会从提示词模拟执行，也不会把旧团队任务或 session Scheduler 记录写进自动化账本。

## M5 项目基础状态

原静态“团队工作流程”页已经由唯一的“跨会话任务”看板替换。M5 状态只读取可信本机 `foundations/state` 安全摘要；它可能显示：尚未使用、正在准备、可以安全落地、真实源不是 Git 根、源脏或可能冲突、等待合并、等待可信质量运行器、质量检查中、本地缺陷待处理、缺陷同步待发送、外部缺陷连接未启用。每种状态只说明系统已自动保存或暂停了什么，以及负责人下一步；看板、摘要或草稿入口都不会自动点击、合并或接受质量结果。

- `source_invalid` 表示当前负责人会话的真实源目录不是 Git 根；系统不会在错误位置创建 foundations 或 worktree。请从真实 Git 根重新打开项目。
- 有待合并 change set、排队/运行中的质量任务、缺陷或外部 outbox 时，计数只用于判断阶段，不含文件、任务或证据明细。
- 协作者固定看到“由主设备负责工作区与质量门禁”，状态卡不提供任何按钮，也不接触 runner 或 connector 凭据。
- 状态卡严格不显示 commit、digest、内部 ref、路径、任务文件、actor、runner key、evidence 或 credential；需要详细处理时由负责人使用 Host 工具查看经过鉴权的结果。

## 顶层项目会话失败后怎样恢复

跨会话任务看板会把真实顶层项目会话的确定失败显示为“顶层会话恢复”。它与 Agent Team 成员恢复不同：系统不会用成员、普通 subagent 或后台隐藏会话替代项目 root。

- **重试同一会话**：只对 Host 证明拥有原 launch batch 的当前直接用户显示。第一次点击进入确认，第二次才提交；真正受益者仍是失败的 reserved child slot 或已收养 root，系统复用同一 Host operation。未出生 child 的 reserved seat 与私有 adoption capability 不会因失败恢复被暂停或销毁；重复点击、刷新或 Host 重启不会创建第二个席位或重复领取任务。
- **请求替代会话**：先按看板的 takeover request 等待负责人响应；到期限后也只有具备项目负责人权限的当前直接用户才能审计接管。系统不会因到期自动唤醒或偷取所有权。
- 替代流程会先一次性保留新席位和该缺陷对应任务，再启动一个真实 top-level session；新会话 ready 后才私下兑换 adoption capability。看到“已保留/正在启动”时不要另开团队成员代替它。
- `outcome_unknown` 表示 Host 无法证明此前创建是否发生。此时刷新/核对状态，不要重试。Stop、adoption 失败、容量不足、权限变化或第三方资源锁都会留下可审计状态并停止自动推进。
- 旧会话迟到不会覆盖 replacement 的新 revision；第三方持有的资源锁也不会随失败 root 一起被偷走。每个新 root 一次仍只能有一个进行中的项目任务。

按钮至少 44px、支持键盘焦点，并用 loading/error 状态说明是否已提交。页面只显示固定错误代码和安全状态，不显示原始 session、Host 诊断、路径或 capability。

## 成员、任务和消息怎么配合

### 成员

成员是独立的、可继续的子代理会话，共享同一工作目录，但上下文彼此隔离。AI 应使用“界面、测试、安全、文档”这类 **2–6 字、简单直白的职责名**，避免“宿主、协调器、执行器、实现者、子代理”等技术称谓；同时给出清楚的角色、初始任务、文件边界和完成标准。新增成员会先持久化注册，再收到正式任务；看到“等待协调员注册完成”的成员尚未开始工作，这是正常的安全流程。

### 任务

任务有三种状态：`pending`（待处理）、`in_progress`（进行中）和 `completed`（已完成）。

- 前置依赖未完成时，后续任务会显示为阻塞，不能认领。
- 认领是原子的；两个成员不会同时成功认领同一个待处理任务。
- 负责人可以分配待处理任务，也可以释放进行中任务后重新分配。
- 完成前置任务会自动解除后续任务的依赖阻塞。

建议先创建任务，再让成员开工。这样即使会话重启，也更容易看出谁负责什么、还缺什么。

### 直接打开成员对话

在团队页点击“代理目录”或画布成员节点，会先通过官方 `sessions.setSubagentCatalogOpen(team.leadSessionId, true)` 打开统一代理目录；再从目录选择健康成员，即可进入该成员的官方可继续只读会话。负责人自身和仍在注册的占位成员不会显示为无效子会话入口。这里适合：

- 补充只针对该成员的细节；
- 查看完整上下文和输出；
- 让成员暂停、修正或继续；
- 使用官方中断能力停止当前回合。

但请记住：普通聊天内容不会自动变成团队任务状态。涉及任务分配、依赖、完成状态或团队关闭时，最好明确要求更新团队任务，并回到负责人会话核对整体状态。

成员之间的团队消息通过固定负责人安全中继，来源是协调消息，不会伪装成你的直接用户消息。成员向正在工作的负责人报告时，消息进入当前回合最近的模型步骤边界，与同批协调上下文一起处理；只有负责人确实空闲时才开启一个后续回合。因此中间报告不会再逐条排成普通用户回合，并在任务结束后集中回放。发送失败时不会自动重复投递；请先检查状态，再手动重发，避免重复工作。

### 必要时自动协作

启用代理团队后，模型可以在同一固定负责人拥有的本地团队范围内执行 `Observe → Avoid → Require → Resolve → Admit → Deliver`：先观察任务和资源声明，能自行避免就不联系；只有精确 Owner、依赖、文件冲突、正式交接或策略强制评审不可绕过时，才发现一个目标并提交一次协作意图。

- `collaboration_discover` 只返回 ACL 允许的最小状态和不可反查的 `routeRef`，不会把原始会话 ID 交给模型；
- `collaboration_intent` 由 Host 重新核对任务、资源和依赖证据，拒绝广播、猜测目标、重复请求、过期状态、环路和无效理由；
- 默认投递到持久、静默、无唤醒 Inbox。请求 L2 唤醒但没有预先授权时会自动降级为 L1 Inbox；当前版本不配置自动 L2 授权；
- `collaboration_inbox` 只能读取和确认当前调用者自己的消息，模型只能在自然协调节点检查，不能轮询；
- 暂停发送方不能发起意图。暂停目标只记录延迟项而不唤醒；显式恢复会改变 `pauseEpoch`，旧项变为 stale，不能自动重放。

持久 Presence、Inbox 和有界顺序审计保存在 Host 私有的 `storages/agent_collaboration.json`；其中的原始路由映射不会投影到模型结果。当前 Host 接入仅覆盖同一固定负责人拥有的本地平级团队；跨用户、跨根会话和 LAN 项目协作仍按后续项目权限层建设，不能把这个本地范围误认为已经开放。

## 多个团队与跨团队协作

同一最外层负责人可以按子目标建立多个**平级团队**，例如“研究”“实现”“发布”，但最多只能同时保留 8 个未关闭团队。它们不是嵌套团队：每个团队都有独立成员和任务，但负责人相同。每队分别受 `maxMembers` 限制，所有团队的活动回合合计受同一个 `maxActiveTurns` 限制。团队总览用于切换和观察，不会因为离开当前团队页面就暂停其他团队。

- 不确定是否应该拆出新团队时，点击“添加协作团队”。它只生成待审草稿，不会直接创建；AI 必须先比较项目目标、现有分工、重复工作和成本。现有团队已足够时应停止并说明原因。
- 确需新增时，由 AI 自动定义同级团队目标、必要成员、主/子模型选择、跨团队依赖和共同负责人中继；用户不需要填写一套团队设计表。
- 多个团队同时活动时，要求状态、发消息、分配任务或关闭团队都应带团队名称或 ID，避免歧义。
- 同一负责人可以让一个团队的任务依赖另一个团队的任务；工作区会把未完成的跨团队前置任务显示为阻塞。
- 只有这个共同的固定负责人可以向另一个平级团队中继消息，并且必须明确来源团队和目标团队。
- 不同根会话拥有的团队默认隔离：不能建立跨根依赖、不能跨根中继，也不能把一个根的成员挂到另一个根的团队。
- 成员仍只属于自己的团队；需要跨团队协调时由负责人汇总最小必要信息，不要假设成员自动共享上下文。

示例：

```text
在“实现团队”创建“集成”任务，让它依赖“研究团队”的“接口核验”任务；
由共同负责人把核验结论中继给实现团队。不要连接其他根会话的团队。
```

## 避免文件冲突

旧团队成员默认共享工作目录；仅创建/分配旧任务**不会**创建 worktree 或自动合并，任务文件范围仍只是协调和预警机制，不是文件锁。M5 Project Foundations 是单独的 Host-only 项目流水线：只有负责人明确领取资源、真实 Git 根有效且声明不冲突时，系统才打开隔离 worktree；成员发布 change set 后仍需经过串行合并和可信质量门禁，不等于保证没有冲突。

推荐规则：

1. 给每个可写任务列出规范化文件路径。
2. 同一文件同一时间只允许一个成员拥有写权限。
3. 审阅者只读检查，通过团队消息提出修改建议，由文件负责人落盘。
4. 工作台出现文件冲突风险时，先暂停其中一个任务；不要让双方继续写后再“碰碰运气”合并。
5. 让负责人在汇总前检查版本控制差异和测试结果。

未使用 M5 Project Foundations 时，仍应由你自己准备并分配独立 worktree。使用 M5 时不要手工猜路径：让负责人通过项目基础工具领取资源并打开系统分配的 worktree；浏览器状态卡只显示安全计数和下一步，不显示路径、commit、digest、ref 或质量证据。

## 模型选择策略

代理团队直接复用 Harness Desktop 现有的**主模型与子代理**路由，不增加第二套“团队模型”设置：

- 固定负责人是团队的规划与汇总“大脑”，始终使用当前主模型，不会为了省成本自动降级到子代理模型。
- 团队成员由 AI 按任务内容在已配置的主模型和子代理模型之间选择。普通实现、检索、整理、测试等任务默认使用子代理模型，以减少成本。
- 高复杂推理、总体架构、安全关键决策，或成员使用子代理模型失败后需要升级处理时，AI 才应为该成员选择主模型。
- 如果你没有单独配置子代理模型，成员自然继承主模型；这不是错误，也不需要额外设置。
- 请在现有“设置 → 模型 → 主模型与子代理”中选择路由。团队工作区不会再提供重复的 Provider、模型或密钥配置 UI。

AI 的选择是成本与任务风险之间的默认策略，不是精确费用保证。若你有模型合规、可用区或预算硬约束，请直接写进团队目标，让负责人在创建成员前遵守。

## 成本与并行度

每个成员都有独立上下文，通常会产生独立的输入、输出和工具调用用量。负责人汇总、成员间中继、失败重试也可能增加用量。因此，不能只用“成员数 × 一次对话”估算成本，当前产品也不承诺某个精确金额。

降低成本的方法：

- 从 1–2 个成员和较低并行度开始，再按需要增加。
- 给成员窄而明确的范围，避免多人重复读完整代码库或重复研究。
- 先做短调查任务，再决定是否值得进入实现。
- 用任务依赖延后暂时不能开工的成员。
- 完成后及时退役成员并关闭团队。
- 在模型服务商的用量页面查看实际 Token、额度和计费；工作台提示只用于提醒，不是账单。

## 成员失败与替换

成员可能因为模型、网络、并发限制、进程重启或任务说明不足进入 `failed` 状态。系统不会悄悄创建替身，也不会自动重放不确定是否送达的消息。

在失败成员所在团队的**负责人会话**打开“代理团队 → 当前工作”。只有成员真实处于 `failed`、团队仍 active、你查看的是固定负责人会话且 Host 安全前提仍成立时，页面才显示“恢复失败成员”：

1. **重试成员**：继续 exact 原成员会话，原 active 任务的 `claimId/leaseEpoch` 保持不变。适用于成员仍有且仅有一个有效 `in_progress` claim 的情况；同一成员已经分配的其他 `pending` 任务保持原 assignment，不需要为此强迫替换。确认后页面显示“正在重试成员…”，连续点击不会产生第二次模型回合；observer 即使先显示 running，只要 exact claim/lease 未变也能正常收敛。
2. **替换成员**：用于原会话不可恢复、任务需重新领取的情况。替换会产生一次新的成员模型启动成本，因此必须在页面再次确认。Host 会保留原 checkpoint、失败与 retirement 审计，撤销旧 claim/lease，把未完成任务放回 pending，先预绑定同一批任务，再创建一个名称为 2–12 字符的**可见同级** replacement；不会使用隐藏 subagent。

两种操作都使用稳定 request 和当前 team revision。`prepared`、child-started、published 和 followup-returned 窗口发生 Host 重启时，系统继续同一个 receipt/exact child，不重复 start 或工作 followup。若 Stop、CAS 或 dispatch 发生在 child 已可能创建/消息已可能送达之后，页面会显示“恢复结果待核对”而不是把它猜成失败并允许再次计费。

看到“恢复结果待核对”后先检查成员/任务与审计，再明确选择“确认已送达”或“确认未送达”。这两个按钮复用原 request：“确认已送达”可用 exact worker 的 pending assignment、匹配 session/claim/lease 的 in-progress claim，或匹配 explicit submission 的 completed task 作为审计证明，并保留现有 task state/claim/result；foreign assignee、legacy migration 或冲突 claim 仍会拒绝。“确认未送达”会先验证 replacement 的所有任务仍是 pending 且绑定 reserved placeholder/child，再停止 exact child（如有）并安全收束；claimed、terminal 或已迁移任务会拒绝并保持待核对，绝不会删除成员后留下悬空任务。paused 团队仍显示 durable 待核对记录，但只提供“确认未送达”，不会把成员重新置为 running。团队最多保存 24 条恢复 receipt；满额时只淘汰最旧已终结 receipt，绝不丢弃 prepared/未决记录，也不会要求关闭仍有任务的团队。

替换成功后，新成员必须按正常流程 claim pending 任务，再携带新的 `claimId/leaseEpoch` 完成；旧成员的迟到 complete 会被 claim fence 拒绝。完成任务、正常运行或已经退役且无未决 receipt 的成员不会显示新恢复按钮。Project board 只向固定负责人显示恢复需要的 opaque 成员引用、名称、revision 和完整未决 request/phase，不显示 session、child 或 claim 内部信息；投影严格计入最终 JSON 的 UTF-8 字节并保持 128 KiB page budget，溢出项以剩余数量诚实标记，较早 receipt 处理后后续项会自动出现。最后仍应检查文件差异和测试，确认失败成员没有留下未经核验的半成品。

## Stop、恢复与外部副作用

用户 Stop 会先把新的暂停 epoch 持久化，再取消排队工作并中断成员。因此，即使某个中断调用失败，迟到的启动、认领或完成写入也不能越过暂停门禁。Stop 后不要依靠刷新页面或重新发送旧提示来“隐式继续”。

恢复分两步：先生成只读 Resume preview，核对哪些任务可继续、哪些成员失败、哪些 claim 已陈旧，以及哪些权限或外部结果仍不确定；预览完成后团队仍是 `paused`。再由最外层直接用户明确提交该 preview。提交时 Host 会比较 request、团队 revision 和 pause epoch，并原子保存 receipt；过期预览会拒绝而不是套用到新状态。健康节点可以继续，异常节点留在 Attention；一个失败成员不会冻结全部团队。重复提交完全相同且已经成功的 request/CAS 只返回既有 receipt，不重复唤醒；旧 token 或同 request 的不同内容会拒绝。

能力显示 `unknown` 表示当前 Host 没有足够事实证明允许或拒绝，并不等于“已授权”。授权投影只有 `unknown`、`human_attested`、`host_verified`：模型声明、普通布尔和成员 checkpoint 不能产生 `host_verified`，也不能把 capability 升级为允许。应先完成绑定当前精确计划 hash 的 Host 验证，再执行受保护操作。成员 checkpoint 和 Todo 里程碑都只是**未验证自报**，不能把 `unknown` 改成允许，也不能冒充 Host 已完成事实。

**Exactly-once 边界：**只有明确参与稳定 command id、receipt 和幂等重放协议的工具，才可以在该协议范围内把重复请求收敛为一次逻辑效果。任意外部 UI 点击、未提供 receipt 的系统操作、第三方网络超时后的动作都不能保证 exactly-once。外部 effect identity 由 Host 导出，模型给出的 `idempotencyKey` 不具权威性。看到 `outcome_unknown` 时不要自动重试；先到权威系统核对是否已发生，再由精确 direct-human root 通过专用 reconciliation 决定继续。

同一 canonical `projectKey` 的另一个最外层会话可以在直接用户授权下预览并提交 adopt/handoff；旧 owner 记录会追加保留，旧 worker 的 claim/lease 被撤销，未完成任务安全回到 `pending`，旧 child 不会被 reparent。跨项目、只因项目名称相同、成员自动发起或没有直接用户授权的接管都会拒绝。旧团队若显示 `legacy_unplanned`，现有活跃 worker 不会被迁移强停，但在按当前计划 recommit 前不能扩张、spawn 或领取新任务。

不同工作根现在拥有真正独立的项目任务数据库和会话启动通道：一个项目的大量写入、慢启动或排队不会占用另一个项目的 SQLite 锁或插件队列；即使使用相同的 request/batch 名称也不会串项目。项目选择只来自当前 exact top-level 会话的 Host 工作根，工具参数不能切换项目。若升级后首次打开旧单项目任务库而 Host 无法唯一证明其工作根，普通 `initialize` 会返回 `PROJECT_ENTRY_LEGACY_BINDING_REQUIRED`；请在确认正确项目的当前 top-level 直接用户回合显式执行一次 `bind_legacy`。Agent、Team member 和普通布尔字段都不能代替该独立动作。它只复制并绑定旧任务数据、不删除旧库；旧会话启动账本不复制，仍由 exact Host binding 安全回退读取、停止或兑换。

## 优雅关闭与强制关闭

**优雅关闭是默认选择。** 负责人会请求成员完成必要清理、提交最终报告并停止接收新工作。先确认任务已完成或明确放弃，再在负责人会话中说：

```text
请先收集所有成员的最终报告，确认没有进行中任务，然后优雅关闭整个团队。
```

如果只想移除一个成员，可以要求“优雅退役成员 `<名称>`”。优雅请求发出后，成员可能暂时显示为正在关闭；等待它结束并再次检查状态。

**强制关闭只用于成员卡死、负责人无法等待或优雅关闭反复失败。** 它会中断成员及其后代回合，可能来不及报告、清理或保存未落盘工作。强制操作后仍应检查工作目录和任务状态。

如果关闭部分失败，团队可能保持活动以便重试，而不是假装已经完全关闭。请查看失败列表，处理对应成员后再次关闭。

## 孤儿团队恢复

“孤儿团队”是指原最外层负责人已不可用，但持久化团队记录仍未关闭。恢复不是接管负责人，也不会继续原团队；当前能力是由**另一个最外层根会话中的直接用户回合**检查候选记录，并在确认后关闭安全的孤儿团队。

处理步骤：

1. 新建或打开一个最外层根会话。
2. 直接要求“检查可恢复的孤儿代理团队”，先只预览，不确认变更。
3. 核对团队 ID、成员和任务。
4. 确认所有工作成员都不再处于配置中、运行中或关闭中。
5. 再明确要求确认恢复/关闭指定孤儿团队。

如果仍有活动成员，系统会拒绝恢复关闭。此时不要绕过检查；先设法停止活动会话，或保留记录等待其变为非活动状态。

## 常见问题

### 为什么启用后没有立即创建团队？

这是正常行为。开关不发送消息，也不会在没有目标时制造请求；自动判断从你下一条普通需求开始。若需求简单或不适合并行，AI 会保持 solo，不会为了展示功能而强行组队。

### 为什么我说“创建团队”却被拒绝？

常见原因是功能未开启、当前不是最外层根会话，或消息不是你在当前回合直接发送。依次检查设置和会话层级。同一负责人可以创建多个平级团队；如果后续操作提示目标不明确，请明确团队名称或团队 ID。

### 为什么成员一直说在等待注册？

成员的第一回合只用于安全注册，注册持久化后才会收到正式工作说明。短暂等待是正常的；长时间不变化时，让负责人检查成员状态，不要直接要求等待中的成员自行开工。

### 为什么任务无法认领？

任务可能已有负责人、不是待处理状态，或仍被未完成的前置任务阻塞。让负责人列出 `blockedBy` 和当前负责人，再完成依赖或释放任务。

### 完成的任务和退役成员去哪里了？

它们没有被删除。完成任务会从“当前工作”自动移入默认收起的“任务历史”；退役成员与普通子代理记录统一保留在官方“代理目录”的历史筛选中；已关闭团队位于团队切换区的“历史团队”。这些入口都保留原有只读审计信息，但不会持续占用主工作区。

### 为什么旧团队工作区不能直接添加成员或修改团队任务？

旧团队状态投影默认仍是只读的。工作区里的“添加成员、添加协作团队、创建任务、协调团队、请求关闭”等快捷按钮只会把建议提示词放入底部官方输入框，不会自动发送或绕过权限。唯一例外是 active 团队中 exact failed worker 的“重试成员 / 替换成员”：它由固定负责人显式确认后调用受信 Host recovery receipt 协议，而不是通用团队写入口。“添加协作团队”也可能得到“不需要新增”的结论。请先检查草稿，再由你亲自发送；真正的团队变更仍由经过鉴权的团队工具执行。

独立的“项目任务”页是另一套能力：项目所有者所在电脑可以明确创建项目任务，并点击服务器给出的状态按钮，但它不会改变旧团队任务，也不能用来添加成员或发送团队消息。

### “协作事件”为什么看不到正文？

Web 工作区只展示投递元数据，完整内容留在经过鉴权的会话中。通过统一“代理目录”打开对应成员会话，或让负责人汇总；不要把“协作事件”当作完整聊天记录。

### 为什么点击“放入输入框”后会自动回到“对话”？

这是为了让输入框只出现在真正的对话视图。系统先保存草稿，再切回“对话”供你检查；这个切换不等于发送，也不会自动触发模型请求。切到“轨迹、代理团队、归档历史、Godot 预览”等页面时输入框会完全隐藏，返回“对话”后草稿仍在。

### 切到其他团队或页面会停止成员吗？

不会。普通切页只卸载当前 UI 的 SSE/轮询订阅，不会调用中断、退役或关闭。团队会在宿主侧继续工作；再次打开团队页会读取最新状态。

### 文件冲突警告会阻止写入吗？

不会。它只是根据进行中任务声明的重叠文件范围发出警告。真正的隔离需要你分配不同文件，或自行准备独立 worktree。

### 重启后团队会消失吗？

团队、任务和成员会话是持久化的；成员会话可继续。重启时处于短暂状态的成员会被校正为可恢复或失败，不会把“正在运行”当成确定事实。重启窗口内投递状态不确定的消息会标为失败，需人工确认后重发。

### 可以同时有多个团队、多个负责人或转移负责人吗？

同一最外层负责人可以同时拥有多个平级团队，但最多 8 个未关闭团队，且**每个团队仍只有这个固定负责人**。每队成员受 `maxMembers` 限制，所有团队共享 `maxActiveTurns`。当前不支持团队内多负责人、领导权转移或嵌套团队；不同根负责人的团队也不能互相连接。

### 关闭团队会删除历史吗？

不会把未完成任务从历史记录中抹掉；成员会话仍使用官方会话机制保存。关闭的重点是停止活动成员并结束团队生命周期。

## 最稳妥的日常流程

1. 在设置中开启功能，并设置较小的成员与并行上限。
2. 从最外层负责人会话打开团队页，只填写目标，让 AI 判断是否需要团队并规划必要成员。
3. 检查草稿后亲自发送；成功提交后界面自动返回“对话”。
4. 让 AI 先建持久任务、依赖和文件范围，再添加必要成员；有独立子目标时可建立同根平级团队。
5. 用团队总览观察各团队、跨团队阻塞、投递状态和冲突风险；普通切页不影响后台工作。
6. 需要细节时直接打开成员会话；跨团队协调、状态变更和关闭都由共同负责人执行，并明确团队 ID。
7. 负责人核验差异、测试和最终报告，随后优雅退役成员并关闭团队；只有卡死时才强制关闭。
