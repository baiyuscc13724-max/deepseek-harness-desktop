## 新增修复及行为证据

### 1. 保存失败污染内存和误停实例

原实现先改 `servers` Map，再 `atomicWrite`；update/delete 还先 stop。将假配置目标换成同名目录以制造 rename 失败后：

- create 留下幽灵行，同一 ID 重试会冲突；
- update 把 revision 从 1 提前推进到 2，旧连接已被停用；
- delete 从内存删除行，旧连接已被停用。

新增 `commit(stagedMap)` 以持久化成功为提交边界，create/update/delete 均先构造独立 Map，成功后再公开内存并处理连接。写失败时保留原行、revision、运行句柄；无需重启即可按相同 ID/revision 明确重试。

初始 3 项行为测试：**0 通过 / 3 失败（退出码 1）**。修复后全部通过。并发测试还验证：待提交 Map 不被 GET/list 看到、create/重复 create/update/delete 串行、同 revision 的第二个并发 update 拒绝且不会再次 stop。

### 2. 重复提交和保存中草稿丢失

原客户端只在 React state 提交后禁用按钮，同一事件轮重复 submit 会产生两个 POST；保存中 input/select/textarea/checkbox 仍能编辑，新草稿又被旧成功回执清空。

新增同步 ref 操作锁，覆盖列表读取和写入；保存期间禁用全部草稿控件，成功才清空，失败保留字段并解除禁用。普通 refresh 不能和 mutation 并行，避免旧列表/revision 迟到覆盖。

行为测试实际执行客户端注册的设置组件和 onSubmit/onClick：双提交 **2 POST→1 POST**，确认框仅一次；七个草稿控件均锁定，拒绝写入后草稿仍在且明确重试成功。

### 3. 写成功与刷新失败混淆

原 `refresh(true)` 吞掉 GET 失败并设置通用 error，外层又设置 saved；实际视图只显示“操作失败”，虽然配置已保存且草稿被清空。首次读取失败还会显示“尚无服务器”。

拆分 write error、read error、success notice：写成功后明确显示配置已更新，GET 失败另用 `role=alert` 告知点击 Refresh 仅重试读取；未取得可信列表时禁用变更按钮，不展示假空列表。Refresh 恢复后重新启用，不重发 POST。

第二轮新增客户端红测：**4 通过 / 2 失败（退出码 1）**，分别暴露双 POST 和保存成功提示被读取错误遮蔽；修复后通过。

### 4. 持久化已提交，但 dispose 拒绝

总审复核指出提交后的连接副作用不能混同写失败。假 dispose 拒绝复现 update/delete 对外抛错，尽管文件已更新/删除；旧 stop 还提前删除运行句柄。

新增明确结果：

- update/delete 的配置已提交结果仍返回；附加 `cleanup: { phase: 'stop-failed', outcome: 'unknown', error: ... }`。
- `stop` 仅在 dispose 成功后移除句柄；失败保留句柄和不确定状态，不声称已停止，不启动替代连接，不在本次操作中自动重试。
- 删除配置后仍有未确认清理的同 ID 句柄时，create 拒绝 `MCP_CLEANUP_REQUIRED`，不覆盖旧句柄或重复启动。
- 对外错误为固定安全文案，不泄露底层 dispose 错误；客户端通过双语 `role=alert` 告知“配置已保存，但无法确认旧连接已停止”，要求用户检查/重启工作台，不重复提交已完成的变更。本轮未执行重启。

该轮红测：**11 通过 / 3 失败（退出码 1）**，分别为 update dispose、delete dispose、客户端缺失告警。修复后通过。

### 5. reconnect 与配置删除/更新共用串行队列

原 reconnect 在 transact 外。现移入同一队列，在队列内部重新检查 revision/enabled。受控延迟 mount 测试验证：删除不能在 reconnect 占用生命周期队列期间进入持久化，随后正确停止新句柄，不留下已删除服务的迟到运行实例。该并发项为修复后的确定性行为验证；不把首次较弱调度测试误报为红测证据。
